BUHURTOS — NOVEMBER 1 PROOF RELEASE BLUEPRINT
============================================================
Target: November 1, 2026

PURPOSE
=======

BuhurtOS must be ready by November 1, 2026 as a polished, stable proof of what the future of armored combat software can look like.

The goal is NOT to build every possible future feature before November 1.

The goal is to launch a convincing, reliable platform that demonstrates the complete vision:

- one place for organizations
- teams
- fighters
- events
- rankings
- rules
- public sport discovery
- team/event management
- fighter signup
- event operations
- statistics
- website embeds
- calendar distribution
- future account delegation

The release must feel intentional and real.

It must not feel like:

- a prototype
- a demo
- a collection of half-built admin pages
- AI-generated placeholder software
- a tournament-only application

The November 1 release should be small enough to finish properly and large enough that people can immediately see where BuhurtOS is going.

============================================================
THE PRODUCT PROMISE
============================================================

BuhurtOS is intended to become:

THE SHARED DIGITAL INFRASTRUCTURE FOR BUHURT / ARMORED COMBAT.

For now, the platform owner can maintain much of the information centrally.

Later, organizations, teams, fighters and organizers can claim and manage the SAME records.

No duplicate pages.
No rebuilding entities.
No changing URLs.
No replacing the backend.
No major migration.

The future adoption path should be:

VIEW BUHURTOS
→ EMBED BUHURTOS
→ FOLLOW BUHURTOS DATA
→ CLAIM EXISTING RECORDS
→ MANAGE THROUGH BUHURTOS
→ RUN OPERATIONS THROUGH BUHURTOS

============================================================
NON-NEGOTIABLE NOVEMBER 1 PRINCIPLE
============================================================

DO NOT add a technology or feature before November 1 unless it does at least one of these:

1. Makes the public platform significantly more impressive.
2. Makes the real Red Deer Rumble workflow usable.
3. Makes BuhurtOS significantly more stable.
4. Makes future organization adoption easier without causing a rewrite.
5. Makes external websites able to use BuhurtOS data.

If it does not meet one of those criteria, defer it.

============================================================
P0 — STABILITY FIRST
============================================================

Before adding more visible features:

- restore completely green frontend CI
- fix current PublicTeamMap TypeScript failure
- diagnose/fix Supabase CI startup failure
- run navigation audit
- run typecheck
- run tests
- run production build
- confirm deploy succeeds

Required release standard:

- zero known critical bugs
- zero known high-severity bugs
- no broken primary navigation
- no buttons that appear actionable but do nothing
- no fake/demo records shown as real
- no fatal errors on supported mobile/desktop layouts
- no private data exposed publicly
- no required workflow that depends on editing SQL manually

Absolute mathematical “bug free” cannot be guaranteed in software.

The November 1 acceptance definition is:

ZERO KNOWN RELEASE-BLOCKING BUGS.

8. FIGHTER SIGNUP
============================================================

Keep the native BuhurtOS signup system.

Do not use Google Forms.

Signup requires an event-specific invitation code.

Example style:

RDR26-ABC123

Authorized code issuers:

- platform super admin
- event member
- host-team member
- event organization member
- governing parent organization member

The code only unlocks event signup.

It does NOT grant admin privileges.

Store submissions privately in Supabase.

Minimum fighter submission fields:

- display/full name
- email
- phone
- team
- experience
- fighting interests/categories
- armor status
- attendance/travel notes
- emergency contact
- additional notes
- consent

Organizer workflow:

PENDING
→ ACCEPT
or
→ DENY

Optional intermediate:
CONTACTED

Only authorized event/team/organization users may see private signup details.

============================================================
9. ACCESS-CODE HIERARCHY
============================================================

Keep the delegated platform access-code architecture already created.

Hierarchy:

platform super admin
→ organization admins
→ clubs/teams
→ captains/coaches/fighters/support

No subgroup may issue a role above its authority.

The server, not the UI, enforces this.

This is the bridge between:

“Garrett manages everything”

and

“organizations manage themselves.”

============================================================
16. PERFORMANCE
============================================================

This is release-critical.

Continue removing:

- N+1 queries
- duplicate directory loads
- unbounded tables
- large unnecessary payloads
- eagerly loaded maps
- repeated RPCs
- unnecessary realtime subscriptions

Already-established direction:

- server-side directory filters
- aggregate organization RPC
- client caching
- lightweight map feed
- lazy map loading
- image lazy loading
- incremental team-card rendering

Required performance behavior:

- public home renders useful content before map finishes
- detail pages do not load entire directories first
- cached navigation feels immediate
- no public route should trigger hundreds of requests
- no huge all-record downloads merely to show a small detail page
