BUHURTOS — MASTER EXECUTION PLAN TO NOVEMBER 1, 2026
======================================================================
Purpose: Detailed source-of-truth execution document for completing the
BuhurtOS proof release by November 1, 2026.

This document expands the November 1 blueprint into an implementation plan.
It explains WHAT must be done, WHY it matters, HOW the parts connect, what
“done” means, what depends on what, and what must be deferred until after
the proof release.

======================================================================
0. EXECUTIVE GOAL
======================================================================

BuhurtOS must prove that armored combat can have one connected digital
platform covering:

- governing organizations
- teams
- fighters
- events
- tournaments
- practices
- demonstrations
- gatherings

- fundraisers
- rankings
- rules

The November 1 release is NOT the final form of BuhurtOS.

The proof release must prioritize:

1. stability
2. clarity
3. real data
4. real workflows
5. public usefulness
6. mobile quality

The release must avoid:

- fake sports data

- duplicate identity systems

- invasive rewrites that jeopardize the deadline
- adding technology simply because it is fashionable

======================================================================
1. RELEASE PHILOSOPHY
======================================================================

The project must be managed using four work classes.

RELEASE BLOCKER
Anything that can break the site, expose data, prevent deployment, corrupt
data, block login, block event access, break signup, or make a primary route
unusable.

CORE PROOF
Features required to demonstrate the BuhurtOS vision.

WOW FEATURE
Features that dramatically improve perception or adoption but are not
required to make the platform function.

POST-LAUNCH
Important future work that should not be allowed to threaten November 1.

Rules:

- Never work on a WOW FEATURE while a RELEASE BLOCKER exists.
- Never start a POST-LAUNCH project while a CORE PROOF feature is unfinished.
- Prefer fewer complete workflows over many partial workflows.
- Never call a feature complete because the page merely renders.
- Every important workflow must be tested end-to-end.

13. FIGHTER SIGNUP — PUBLIC FLOW
======================================================================

Objective:
Replace external form dependence with a native BuhurtOS intake system.

Flow:

1. Visitor opens event.
2. Visitor chooses Fighter Signup.
3. Invite-code screen appears.
4. Visitor enters event code.
5. Server validates code.
6. Valid code unlocks form.
7. Fighter submits.
8. Submission stored privately.
9. Confirmation shown.
10. Organizer reviews later.

Required code format:

Event-recognizable prefix.

Example:

RDR26-ABC123

Code must be stored hashed.

Code controls event signup only.

It must NOT grant platform permissions.

Fields:

- name
- email
- phone
- team
- experience
- categories/interests
- armor status
- travel/attendance notes
- emergency contact
- additional notes
- consent

Security:

- anonymous can validate code
- anonymous can submit with valid code
- anonymous cannot read submissions
- only authorized hierarchy members can review

DONE WHEN:

- invalid code fails
- valid code succeeds
- submission stored
- no private cross-user exposure
